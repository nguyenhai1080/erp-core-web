# Manual period revenue and USD/VND adaptation

Owner correction: VNATEL/GST amounts are entered from an agreed spreadsheet or directly; no MOVITEL OCR, share-rate, fixed deduction, or tax calculation is inferred. Donor v61 `30_Revenue.js` supplies draft/submit/approve provenance and `53_InputRecon_AP.js` supplies period/currency FX lookup. Explicit owner override replaces donor gross-to-share arithmetic with GST entitlement supplied by the user. VNATEL is GST's output counterparty/AR debtor.

## Runtime
- Quản lý Doanh thu: direct rows or strict first-sheet XLSX / UTF-8 CSV preview (100 rows, 5 MB); optional immutable source PDF/PNG/JPEG or matching spreadsheet. Columns: period, serviceCode, contractCode, currency, amount, deduction, fxRate, note. Currency must match an effective Active output contract/service link. Child services are rejected for manual monthly totals.
- `amount` is GST entitlement in the native currency. Optional deduction is explicitly entered, defaults to zero and is never calculated from MOVITEL sharing. USD has two decimals; VND is integer. Both revenue equivalents use the supplied positive VND/USD rate. Net payable = entered entitlement minus entered deduction.
- Draft → Pending Approval → Approved. Existing RECON_UPLOAD/RECON_REVIEW/RECON_APPROVE permissions are retained; no role grants. Tenant, origin/CSRF, expected timestamp, period locks, source checksums and atomic transactions protect writes. No revenue exists before approval. Parent/service/partner/period duplicate checks prevent concurrent double posting. Approved rows are immutable; only unapproved drafts may be cancelled and recreated.
- Approved reconciliation payload and checksum feed existing Revenue → Invoice → AR. PDF-origin sources keep their signed-PDF checks; manual-origin sources verify the approved entry and optional source file instead. Invoice uses TOTAL parent rows only, grouped by native currency. VND invoices use a currency-labelled GST PDF and a clean VND XLSX export; USD templates remain unchanged. Unverified USD-template bank account details are omitted from VND documents.
- Native VND receipt reduces VND AR, stores `paidUsd=0`, positive `paidVnd`, FX=1 and `allocationCurrency=VND`. Existing USD allocations retain positive USD plus actual VND receipt. Additive migration defaults all existing payment rows to USD and does not change financial amounts. Partial/full payments, idempotent retry, stale guard and overpayment rejection apply to both.
- Revenue list and Dashboard display both currencies. Stored manual FX is frozen at approval; an immutable company/period reporting rate can convert legacy USD rows missing FX. Missing FX yields incomplete/null normalized totals, never a silent zero or rate of one. AR subtotals are separated by native currency. Child amounts never enter global revenue totals. Cash balance/AP remain unavailable until their full ledgers exist.

## Validation
Disposable PostgreSQL only: 260 integration checks plus 67 donor financial checks; existing Dashboard characterization; separate CSV/XLSX, currency conversion and VND allocation characterization. Full workspace build. No live revenue, invoice, payment, FX, company identity, role or source data is created by acceptance verification.

This release provides commercial invoice PDF/XLSX documents. It does not submit electronic tax invoices or automatically apply VAT rules. Historical GST template settings do not determine current VNATEL commercial terms.
